# Протокол обмена устройства с VPS

## 1. Назначение

Документ описывает сетевой и прикладной протокол обмена между:

- устройством на базе `Arduino Uno/Nano + ESP-01`;
- внешним сервером на `VPS`.

Протокол предназначен для:

- получения устройством команд с сервера;
- отправки подтверждений выполнения;
- передачи состояния системы;
- передачи событий и ошибок;
- проверки доступности;
- синхронизации времени.

## 2. Базовые принципы

Протокол проектируется с учётом ограничений `Uno/Nano`:

- без JSON в прошивке;
- без `String`;
- с короткими текстовыми сообщениями;
- с фиксированными буферами;
- с минимальным количеством полей.

Принята модель:

- устройство само делает исходящие HTTP-запросы к `VPS`;
- сервер не инициирует соединение с устройством напрямую;
- в каждый момент сервер отдаёт устройству не более одной команды;
- каждая команда имеет `command_id`;
- устройство обязано вернуть `ACK`, затем `RES` или `ERR`.

## 3. Транспортный уровень

Используется:

- `HTTP/1.1`;
- кодировка тела: `ASCII` или совместимая с ней `UTF-8` без специальных символов;
- полезная нагрузка передаётся как `text/plain`.

Рекомендуемые заголовки:

```text
Content-Type: text/plain
Connection: close
X-Device-Token: <token>
```

Примечание:

- для `ESP-01` проще закрывать соединение после каждого запроса;
- `keep-alive` в первой версии не требуется.

## 4. Адреса и идентификация

Каждое устройство имеет:

- `device_id` — уникальный идентификатор устройства;
- `device_token` — секрет для авторизации запросов.

Пример:

```text
device_id = greenhouse-01
device_token = 7A3F19C2B8D4
```

Все запросы отправляются на:

```text
/api/v1/device/{device_id}/...
```

Авторизация в первой версии:

- `device_id` передаётся в URL;
- `device_token` передаётся в заголовке `X-Device-Token`.

Если реализация заголовков через `ESP-01` окажется неудобной, допускается запасной вариант:

```text
/api/v1/device/{device_id}/commands?token=<device_token>
```

Но основным вариантом лучше считать заголовок.

## 5. Формат прикладного сообщения

Все сообщения в теле HTTP имеют общий формат:

```text
TYPE|VERSION|ID|NAME|ARG1=VALUE|ARG2=VALUE|...
```

Где:

- `TYPE` — тип сообщения;
- `VERSION` — версия протокола, сейчас `v1`;
- `ID` — идентификатор команды или сообщения;
- `NAME` — имя команды, события или результата;
- далее идут параметры `KEY=VALUE`.

### 5.1 Ограничения на символы

Во избежание сложного экранирования в `v1` вводятся ограничения:

- разделитель полей: `|`
- разделитель пары: `=`
- значения не должны содержать `|` и `=`
- строковые значения рекомендуется ограничить набором:
  - `A-Z`
  - `a-z`
  - `0-9`
  - `_`
  - `-`
- числовые значения передаются в десятичном виде

Если позже понадобится передавать произвольный текст, это будет вынесено в `v2`.

### 5.2 Типы сообщений

Поддерживаемые типы:

- `CMD` — команда от сервера устройству;
- `ACK` — устройство приняло команду;
- `RES` — команда успешно выполнена;
- `ERR` — команда завершилась ошибкой;
- `STATE` — текущее состояние системы;
- `EVT` — событие системы;
- `PING` — heartbeat или ping;
- `PONG` — ответ на ping;
- `TIME` — синхронизация времени.

## 6. HTTP endpoints

### 6.1 Получение команды

Запрос:

```http
GET /api/v1/device/greenhouse-01/commands HTTP/1.1
Host: example.com
X-Device-Token: 7A3F19C2B8D4
Connection: close
```

Варианты ответа:

1. Нет команды:

```http
HTTP/1.1 204 No Content
```

2. Есть команда:

```http
HTTP/1.1 200 OK
Content-Type: text/plain

CMD|v1|101|GET_SNAPSHOT
```

3. Ошибка авторизации:

```http
HTTP/1.1 401 Unauthorized
```

Правило:

- сервер должен возвращать не более одной команды за один запрос;
- если очередь пуста, предпочтителен `204 No Content`.

### 6.2 Подтверждение получения команды

Запрос:

```http
POST /api/v1/device/greenhouse-01/ack HTTP/1.1
Host: example.com
Content-Type: text/plain
X-Device-Token: 7A3F19C2B8D4
Connection: close

ACK|v1|101|ACCEPTED
```

Успешный ответ:

```http
HTTP/1.1 200 OK
```

### 6.3 Результат выполнения команды

Успешное выполнение:

```http
POST /api/v1/device/greenhouse-01/result HTTP/1.1
Host: example.com
Content-Type: text/plain
X-Device-Token: 7A3F19C2B8D4
Connection: close

RES|v1|101|DONE
```

Выполнение с ошибкой:

```http
POST /api/v1/device/greenhouse-01/result HTTP/1.1
Host: example.com
Content-Type: text/plain
X-Device-Token: 7A3F19C2B8D4
Connection: close

ERR|v1|101|INVALID_ARG|FIELD=MODE
```

Успешный ответ:

```http
HTTP/1.1 200 OK
```

### 6.4 Публикация состояния

Запрос:

```http
POST /api/v1/device/greenhouse-01/state HTTP/1.1
Host: example.com
Content-Type: text/plain
X-Device-Token: 7A3F19C2B8D4
Connection: close

STATE|v1|0|LIGHT|STATE=ON|TIMER=1|TEMPLATE=1|MANUAL=HIGH
```

Успешный ответ:

```http
HTTP/1.1 200 OK
```

### 6.5 Публикация события

Запрос:

```http
POST /api/v1/device/greenhouse-01/event HTTP/1.1
Host: example.com
Content-Type: text/plain
X-Device-Token: 7A3F19C2B8D4
Connection: close

EVT|v1|0|WATERING_STARTED|PLANT=2
```

### 6.6 Heartbeat

Запрос:

```http
POST /api/v1/device/greenhouse-01/heartbeat HTTP/1.1
Host: example.com
Content-Type: text/plain
X-Device-Token: 7A3F19C2B8D4
Connection: close

PING|v1|0|UPTIME=12345|WIFI=1|RSSI=-67
```

Ответ:

```http
HTTP/1.1 200 OK
Content-Type: text/plain

PONG|v1|0
```

### 6.7 Синхронизация времени

Запрос:

```http
GET /api/v1/device/greenhouse-01/time HTTP/1.1
Host: example.com
X-Device-Token: 7A3F19C2B8D4
Connection: close
```

Ответ:

```http
HTTP/1.1 200 OK
Content-Type: text/plain

TIME|v1|0|EPOCH=1760000000
```

Если время недоступно:

```http
HTTP/1.1 503 Service Unavailable
```

## 7. Жизненный цикл команды

Для каждой команды используется такая последовательность:

1. Устройство запрашивает `/commands`.
2. Сервер возвращает `CMD|...` либо `204`.
3. Устройство валидирует формат сообщения.
4. Если команда корректна, устройство отправляет `ACK`.
5. Устройство выполняет команду.
6. Устройство отправляет `RES` или `ERR`.
7. При необходимости дополнительно отправляет `STATE` или `EVT`.

Пример:

```text
CMD|v1|150|LIGHT_MANUAL|STATE=ON|PRIORITY=HIGH|DURATION=1800
ACK|v1|150|ACCEPTED
RES|v1|150|DONE
STATE|v1|0|LIGHT|STATE=ON|MANUAL=HIGH
```

## 8. Идентификаторы команд и защита от дублей

Требования:

- `command_id` назначается сервером;
- `command_id` должен быть уникальным для устройства;
- устройство хранит `last_processed_command_id`;
- если приходит уже выполненная команда, устройство не должно выполнять её повторно.

Поведение при дубле:

- если команда уже была завершена успешно, устройство может повторно отправить `RES`;
- если команда уже была завершена с ошибкой, устройство может повторно отправить `ERR`;
- если хранятся только последние `N` состояний, допускается отправка:

```text
ERR|v1|150|DUPLICATE_COMMAND
```

## 9. Форматы сообщений

### 9.1 `CMD`

Формат:

```text
CMD|v1|<command_id>|<command_name>|KEY=VALUE|...
```

Примеры:

```text
CMD|v1|101|GET_SNAPSHOT
CMD|v1|102|LIGHT_TIMER_ENABLE|STATE=1
CMD|v1|103|LIGHT_TEMPLATE_SELECT|INDEX=1
CMD|v1|104|LIGHT_MANUAL|STATE=ON|PRIORITY=LOW
CMD|v1|105|LIGHT_MANUAL|STATE=OFF|PRIORITY=HIGH|DURATION=1800
CMD|v1|106|PLANT_MODE|PLANT=2|MODE=MOISTURE
CMD|v1|107|PLANT_THRESHOLD_SET|PLANT=2|VALUE=450
CMD|v1|108|WATERING_MANUAL_START|MASK=5
CMD|v1|109|TIME_SYNC|EPOCH=1760000000
```

### 9.2 `ACK`

Формат:

```text
ACK|v1|<command_id>|ACCEPTED
```

Пример:

```text
ACK|v1|105|ACCEPTED
```

### 9.3 `RES`

Формат:

```text
RES|v1|<command_id>|DONE
```

Допустимые значения `NAME` для `RES` в `v1`:

- `DONE`
- `UNCHANGED`

Примеры:

```text
RES|v1|101|DONE
RES|v1|103|UNCHANGED
```

### 9.4 `ERR`

Формат:

```text
ERR|v1|<command_id>|<error_code>|KEY=VALUE|...
```

Примеры:

```text
ERR|v1|103|INVALID_ARG|FIELD=INDEX
ERR|v1|104|OUT_OF_RANGE|FIELD=DURATION
ERR|v1|107|UNKNOWN_PLANT|PLANT=9
ERR|v1|108|EXECUTION_ERROR
ERR|v1|109|DUPLICATE_COMMAND
```

### 9.5 `STATE`

Формат:

```text
STATE|v1|0|<state_block>|KEY=VALUE|...
```

Рекомендуемые блоки:

- `SNAPSHOT`
- `LIGHT`
- `PLANT`
- `SYSTEM`

Примеры:

```text
STATE|v1|0|LIGHT|STATE=ON|TIMER=1|TEMPLATE=1|MANUAL=HIGH
STATE|v1|0|PLANT|INDEX=1|MOISTURE=430|THRESHOLD=500|MODE=MOISTURE|WATERING=0
STATE|v1|0|SYSTEM|WIFI=1|SERVER=1|ERR=0
```

### 9.6 `EVT`

Формат:

```text
EVT|v1|0|<event_name>|KEY=VALUE|...
```

Примеры:

```text
EVT|v1|0|DEVICE_BOOT
EVT|v1|0|LIGHT_CHANGED|STATE=ON
EVT|v1|0|WATERING_STARTED|PLANT=2
EVT|v1|0|WIFI_RECONNECTED
EVT|v1|0|CONFIG_RESTORED|SOURCE=EEPROM
```

### 9.7 `PING` и `PONG`

Форматы:

```text
PING|v1|0|UPTIME=12345|WIFI=1|RSSI=-67
PONG|v1|0
```

### 9.8 `TIME`

Формат:

```text
TIME|v1|0|EPOCH=1760000000
```

## 10. Набор команд `v1`

### 10.1 Системные команды

- `GET_SNAPSHOT`
- `TIME_SYNC`
- `CONFIG_SAVE`
- `CONFIG_LOAD`
- `DEVICE_REBOOT`

### 10.2 Команды света

- `LIGHT_TIMER_ENABLE`
- `LIGHT_TIMER_DISABLE`
- `LIGHT_TEMPLATE_SELECT`
- `LIGHT_TEMPLATE_SAVE`
- `LIGHT_MANUAL`
- `LIGHT_MANUAL_CANCEL`

### 10.3 Команды полива

- `PLANT_MODE`
- `PLANT_THRESHOLD_SET`
- `WATERING_MANUAL_START`
- `WATERING_MANUAL_STOP`

## 11. Аргументы команд

### 11.1 `GET_SNAPSHOT`

Без аргументов.

Ответ:

- `RES|...|DONE`
- затем один или несколько `STATE`.

### 11.2 `TIME_SYNC`

Аргументы:

- `EPOCH` — Unix time в секундах

Пример:

```text
CMD|v1|201|TIME_SYNC|EPOCH=1760000000
```

### 11.3 `LIGHT_TIMER_ENABLE`

Аргументы:

- `STATE=1`

Допускается также форма без аргументов, если сервер и устройство согласуют её заранее.

### 11.4 `LIGHT_TIMER_DISABLE`

Аргументы:

- `AFTER=ON` или `AFTER=OFF`

Это покрывает требование ТЗ о явном состоянии света после отключения таймера.

Пример:

```text
CMD|v1|202|LIGHT_TIMER_DISABLE|AFTER=OFF
```

### 11.5 `LIGHT_TEMPLATE_SELECT`

Аргументы:

- `INDEX` — индекс шаблона

### 11.6 `LIGHT_TEMPLATE_SAVE`

В `v1` рекомендуется сохранять шаблоны по частям, чтобы не передавать слишком длинную строку.

Минимальный вариант:

```text
CMD|v1|203|LIGHT_TEMPLATE_SAVE|INDEX=1|NAME=DAY
CMD|v1|204|LIGHT_TEMPLATE_INTERVAL|INDEX=1|POS=0|START=480|END=1320|STATE=ON
CMD|v1|205|LIGHT_TEMPLATE_INTERVAL|INDEX=1|POS=1|START=1320|END=1440|STATE=OFF
```

Примечание:

- `LIGHT_TEMPLATE_INTERVAL` нужно сразу считать частью `v1`, если шаблоны будут редактироваться удалённо.

### 11.7 `LIGHT_MANUAL`

Аргументы:

- `STATE=ON|OFF`
- `PRIORITY=HIGH|LOW`
- `DURATION=<seconds>` — необязательный аргумент

Примеры:

```text
CMD|v1|206|LIGHT_MANUAL|STATE=ON|PRIORITY=LOW
CMD|v1|207|LIGHT_MANUAL|STATE=OFF|PRIORITY=HIGH|DURATION=1800
```

### 11.8 `LIGHT_MANUAL_CANCEL`

Без аргументов.

### 11.9 `PLANT_MODE`

Аргументы:

- `PLANT=<index>`
- `MODE=TIMER|MOISTURE|DISABLED`

### 11.10 `PLANT_THRESHOLD_SET`

Аргументы:

- `PLANT=<index>`
- `VALUE=<threshold>`

### 11.11 `WATERING_MANUAL_START`

Аргументы:

- `MASK=<bitmask>`

Пример:

```text
CMD|v1|208|WATERING_MANUAL_START|MASK=5
```

Здесь `MASK=5` означает двоичную маску `0101`, то есть полив растений `0` и `2`.

Если битовые маски окажутся неудобны для серверной стороны, можно заменить на:

```text
CMD|v1|208|WATERING_MANUAL_START|PLANT=0
CMD|v1|209|WATERING_MANUAL_START|PLANT=2
```

Но для прошивки маска обычно эффективнее.

### 11.12 `WATERING_MANUAL_STOP`

Аргументы:

- `MASK=<bitmask>`

## 12. Состояние системы

### 12.1 Блок `LIGHT`

Поля:

- `STATE=ON|OFF`
- `TIMER=0|1`
- `TEMPLATE=<index>`
- `MANUAL=NONE|LOW|HIGH`

Пример:

```text
STATE|v1|0|LIGHT|STATE=ON|TIMER=1|TEMPLATE=1|MANUAL=LOW
```

### 12.2 Блок `PLANT`

Поля:

- `INDEX=<plant_index>`
- `MOISTURE=<value>`
- `THRESHOLD=<value>`
- `MODE=TIMER|MOISTURE|DISABLED`
- `WATERING=0|1`

Пример:

```text
STATE|v1|0|PLANT|INDEX=2|MOISTURE=410|THRESHOLD=500|MODE=MOISTURE|WATERING=1
```

### 12.3 Блок `SYSTEM`

Поля:

- `WIFI=0|1`
- `SERVER=0|1`
- `ERR=<code>`
- `UPTIME=<seconds>`

Пример:

```text
STATE|v1|0|SYSTEM|WIFI=1|SERVER=1|ERR=0|UPTIME=12345
```

### 12.4 Полный snapshot

Для `GET_SNAPSHOT` рекомендуется отправлять несколько сообщений `STATE`, а не одну длинную строку.

Пример:

```text
STATE|v1|0|LIGHT|STATE=ON|TIMER=1|TEMPLATE=1|MANUAL=HIGH
STATE|v1|0|PLANT|INDEX=0|MOISTURE=390|THRESHOLD=450|MODE=MOISTURE|WATERING=0
STATE|v1|0|PLANT|INDEX=1|MOISTURE=610|THRESHOLD=550|MODE=TIMER|WATERING=1
STATE|v1|0|SYSTEM|WIFI=1|SERVER=1|ERR=0|UPTIME=12345
```

## 13. Коды ошибок

Рекомендуемые коды:

- `UNKNOWN_COMMAND`
- `INVALID_ARG`
- `MISSING_ARG`
- `OUT_OF_RANGE`
- `UNKNOWN_PLANT`
- `UNKNOWN_TEMPLATE`
- `DUPLICATE_COMMAND`
- `BUSY`
- `STORAGE_ERROR`
- `TRANSPORT_ERROR`
- `EXECUTION_ERROR`

Примеры:

```text
ERR|v1|301|MISSING_ARG|FIELD=MODE
ERR|v1|302|UNKNOWN_PLANT|PLANT=7
ERR|v1|303|OUT_OF_RANGE|FIELD=DURATION
ERR|v1|304|STORAGE_ERROR
```

## 14. Поведение при сетевых ошибках

Если запрос не удался:

- устройство не должно считать команду подтверждённой сервером;
- запрос можно повторить ограниченное число раз;
- число повторов задаётся константой;
- после исчерпания повторов в лог пишется событие транспорта.

Рекомендуемые константы:

- `POLL_INTERVAL_MS = 5000`
- `HEARTBEAT_INTERVAL_MS = 30000`
- `HTTP_RETRY_COUNT = 3`
- `HTTP_TIMEOUT_MS = 5000`

Если не удалось отправить `STATE` или `EVT`:

- сообщение можно сохранить во внутреннюю очередь короткого размера;
- при переполнении очереди старые события допускается вытеснять новыми.

## 15. Поведение при перезагрузке

После старта устройство должно:

1. Загрузить конфиг.
2. Поднять Wi-Fi.
3. Выполнить синхронизацию времени.
4. Отправить событие:

```text
EVT|v1|0|DEVICE_BOOT
```

5. Отправить текущее состояние.

Если время синхронизировать не удалось:

- таймерные режимы должны работать только если есть локальный RTC;
- если RTC нет, сервер должен как можно быстрее передать `TIME`.

## 16. Минимальный серверный контракт для MVP

Для первого рабочего прототипа достаточно реализовать на `VPS`:

- `GET /commands`
- `POST /ack`
- `POST /result`
- `POST /state`
- `POST /event`
- `GET /time`

Минимальные правила сервера:

- проверка `device_id` и `device_token`;
- хранение очереди команд по каждому устройству;
- выдача не более одной команды на запрос;
- логирование `ACK`, `RES`, `ERR`, `STATE`, `EVT`;
- возможность вручную добавить команду в очередь.
