**Техническое задание**

**Система обмена командами между внешним сервером и Arduino-системой управления светом и поливом![ref1]**

1. **Общая информация**

Необходимо разработать модуль взаимодействия между внешним сервером и системой управления на базе Arduino.

Модуль должен обеспечивать:

- приём команд от внешнего сервера;
- передачу состояния системы на сервер;
- хранение текущего состояния и конфигурации;
- логирование событий и ошибок;
- документацию используемого текстового протокола обмена.

Сама логика обработки команд внутри основной системы будет реализовываться другим разработчиком отдельно.

В рамках данной задачи необходимо реализовать именно интерфейс обмена и структуру взаимодействия.![ref2]

2. **Общие требования**
1. **Формат обмена**

Формат текстовых команд остаётся на усмотрение разработчика. Допускается использование:

- JSON;
- собственного текстового протокола;
- любого другого текстового формата.

Обязательные требования:

- формат должен быть документирован;
- документация должна позволять другому разработчику реализовать обработчик команд;
- формат должен поддерживать расширяемость.![ref2]
2. **Архитектура взаимодействия**

Способ передачи данных выбирается разработчиком:

- HTTP;
- MQTT;
- WebSocket;
- TCP/UDP;
- Serial;
- другое решение.

Необходимо предусмотреть:

- получение команд извне;
- отправку ответов и состояния системы;
- подтверждение выполнения команд;
- обработку ошибок.![ref3]
3. **Хранение состояния**

После перезагрузки системы должны сохраняться:

- настройки таймеров;
- шаблоны освещения;
- состояния растений;
- пороги влажности;
- активные режимы;
- текущее состояние света;
- прочие конфигурационные параметры.![ref1]
4. **Логирование**

Необходимо реализовать логирование:

- входящих команд;
- ошибок;
- изменения состояний;
- переключения режимов;
- действий системы.![ref1]
3. **Функционал управления светом![ref2]**
1. **Управление светом по таймеру**

Система должна поддерживать режим автоматического управления светом по расписанию.

**Требования**

- Таймер может быть:
  - включён;
  - выключен.
- Таймер состоит из набора временных интервалов.
- Каждый интервал определяет состояние света:
  - включён;
  - выключен.
- Количество интервалов не ограничено.
- Внутри одного таймера пересечение интервалов запрещено.
- При выключении таймера необходимо явно задавать:
  - состояние света после отключения таймера.![ref2]

**Шаблоны таймеров**

Система должна поддерживать шаблоны расписаний. Требования:

- возможность создавать несколько шаблонов;
- возможность переключаться между шаблонами;
- активным может быть только один шаблон;
- шаблоны должны сохраняться после перезагрузки.![ref4]
2. **Ручное управление светом**

Система должна поддерживать ручное изменение состояния света. **Возможности**

Ручная команда должна позволять:

- установить состояние света:
  - включить;
  - выключить;
- указать длительность действия команды (опционально).

Пример:

- включить свет на 30 минут.![ref4]

**Приоритеты ручного режима**

Ручной режим должен поддерживать два приоритета.

**Высший приоритет**

- таймер полностью игнорируется;
- состояние света определяется только ручной командой;
- после завершения ручного режима управление возвращается таймеру.![ref1]

**Низший приоритет**

- ручной режим действует до ближайшего события таймера;
- при наступлении события таймера состояние света изменяется согласно расписанию;
- далее система продолжает работу по таймеру.![ref3]

**Завершение ручного режима**

После завершения ручного режима:

- если таймер включён:
  - состояние света должно соответствовать текущему состоянию по таймеру;
- если таймер выключен:
  - состояние света изменяется на противоположное текущему.
4. **Функционал управления поливом![ref2]![ref4]**
1. **Полив по таймеру**

Система должна поддерживать автоматический полив по расписанию.

**Требования**

- Полив запускается в заданные моменты времени.
- Отключение полива реализуется отдельной логикой.
- Для каждого растения должен быть доступен выбор режима работы.![ref3]
2. **Полив по потребности**

Система должна поддерживать автоматический полив на основе влажности почвы.

**Требования**

- У каждого растения имеется отдельный датчик влажности.
- Для каждого растения задаётся порог влажности.
- Если влажность ниже порога:
  - запускается полив.![ref3]
3. **Режимы полива растений**

Для каждого растения должен задаваться режим работы:

1. Полив по таймеру
1. Полив по потребности
1. Полив отключён![ref2]

**Особенности**

- В режиме "полив отключён":
  - автоматический полив не выполняется;
  - ручной полив остаётся доступным.
- Настройки режима должны сохраняться после перезагрузки.![ref2]
4. **Ручной режим полива**

Система должна поддерживать ручной запуск полива.

**Требования**

- Возможность выбора любого множества растений.
- Ручной полив должен работать независимо от выбранного режима растения.
- Длительность ручного полива в команде не требуется.![ref3]
5. **Обратная связь от системы**

Система должна предоставлять внешнему серверу информацию о текущем состоянии.![ref3]

1. **Информация о системе**

Необходимо обеспечить возможность получения:

**Свет**

- текущее состояние света;
- активный шаблон;
- состояние таймера;
- активный ручной режим.

**Полив**

- список растений;
- текущая влажность каждого растения;
- порог влажности;
- режим работы растения;
- активность полива.

**Система**

- ошибки;
- состояние подключения;
- статус выполнения команд.
2. **Подтверждение команд![ref2]**

На каждую команду система должна возвращать результат выполнения. Минимально:

- успешно;
- ошибка;
- причина ошибки.![ref4]
6. **Требования к расширяемости**

Архитектура должна предусматривать возможность расширения системы. В будущем возможно:

- несколько независимых источников света;
- несколько помп;
- дополнительные датчики;
- новые типы устройств.

Необходимо спроектировать формат команд и внутреннюю структуру с учётом масштабирования.![ref2]

7. **Документация**

Разработчик должен предоставить:

- описание архитектуры;
- описание используемого протокола;
- формат команд;
- примеры запросов и ответов;
- описание ошибок;
- описание хранения состояния;
- описание механизма восстановления после перезагрузки.![ref1]
8. **Дополнительно (желательно)**

Желательно предусмотреть:

- версионирование протокола;
- возможность добавления новых типов команд без нарушения совместимости;
- механизм heartbeat/ping для проверки доступности системы;
- возможность получения полного snapshot состояния системы одной командой.
