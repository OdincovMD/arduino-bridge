# Архитектура системы обмена для Arduino Uno/Nano + ESP-01

## 1. Цель

Реализовать модуль обмена между внешним сервером и Arduino-системой управления светом и поливом.

В рамках данного модуля решаются задачи:

- получение команд от сервера;
- подтверждение выполнения команд;
- публикация текущего состояния;
- хранение конфигурации и её восстановление после перезагрузки;
- логирование событий и ошибок;
- предоставление стабильного интерфейса для разработчика бизнес-логики.

В рамках данного модуля не реализуется сложная предметная логика управления расписаниями, приоритетами и алгоритмами полива. Для неё задаются интерфейсы и структуры данных.

## 2. Ограничения платформы

Целевая платформа:

- `Arduino Uno` или `Arduino Nano`;
- `ESP8266 ESP-01` как Wi-Fi модуль;
- связь с `ESP-01` через UART;
- постоянное хранилище `EEPROM`.

Ключевые ограничения:

- очень маленький объём RAM;
- ограниченный объём flash;
- нежелательно использовать `String`;
- нежелателен JSON-парсинг на стороне `Uno/Nano`;
- нельзя держать большие логи в `EEPROM`;
- количество шаблонов, интервалов, растений и событий должно быть ограничено константами.

Следствие: архитектура строится вокруг фиксированных буферов, `struct`, `char[]`, компактного текстового протокола и периодического опроса сервера.

## 3. Общая схема взаимодействия

Выбранная модель:

- `Arduino` является главным контроллером состояния;
- `ESP-01` используется как транспортный модуль;
- устройство само инициирует обмен с сервером;
- сервер не открывает сессию в устройство напрямую.

Схема обмена:

1. Устройство подключается к Wi-Fi.
2. Устройство периодически отправляет heartbeat.
3. Устройство периодически делает запрос на получение новых команд.
4. Сервер возвращает 0 или 1 команду за запрос.
5. Устройство валидирует команду и отправляет `ACK`.
6. Устройство передаёт команду в слой исполнения.
7. После завершения отправляет `RESULT` или `ERROR`.
8. При изменении состояния публикует `STATE` или `EVENT`.

Преимущества данной схемы:

- не требуется входящий сервер на устройстве;
- проще работать через `ESP-01 AT`;
- проще восстановление после обрыва Wi-Fi;
- меньше риск зависаний из-за долгоживущих соединений.

## 4. Выбранный транспорт

Рекомендуемый транспорт между устройством и сервером: `HTTP`.

Причины:

- проще отлаживать;
- естественно ложится на схему polling;
- не требует полноценного MQTT-клиента на слабом контроллере;
- серверную сторону легко расширять.

Использование `ESP-01`:

- `AT+CWMODE`, `AT+CWJAP` для подключения к Wi-Fi;
- `AT+CIPSTART` для установки TCP-соединения;
- `AT+CIPSEND` для отправки HTTP-запроса;
- чтение HTTP-ответа из UART;
- при ошибке соединения выполняется повторная инициализация транспорта.

## 5. Формат прикладного протокола

Для полезной нагрузки используется компактный текстовый протокол.

Базовый формат:

```text
TYPE|v1|ID|NAME|ARG1=VALUE|ARG2=VALUE|...
```

Где:

- `TYPE` — тип сообщения;
- `v1` — версия протокола;
- `ID` — идентификатор команды или сообщения;
- `NAME` — имя команды или события;
- далее список параметров `KEY=VALUE`.

Поддерживаемые типы сообщений:

- `CMD` — команда от сервера устройству;
- `ACK` — команда принята к обработке;
- `RES` — успешный результат выполнения;
- `ERR` — ошибка валидации или выполнения;
- `STATE` — снимок или частичное состояние;
- `EVT` — событие системы;
- `PING` — проверка доступности;
- `PONG` — ответ на проверку доступности.

Примеры:

```text
CMD|v1|101|GET_SNAPSHOT
ACK|v1|101|ACCEPTED
RES|v1|101|DONE

CMD|v1|102|LIGHT_MANUAL|STATE=ON|PRIORITY=HIGH|DURATION=1800
ACK|v1|102|ACCEPTED
RES|v1|102|DONE

CMD|v1|103|PLANT_MODE|PLANT=2|MODE=MOISTURE
ERR|v1|103|INVALID_ARG|MODE

STATE|v1|0|SNAPSHOT|LIGHT=ON|TIMER=1|TEMPLATE=DAY|MANUAL=HIGH
EVT|v1|0|WATERING_STARTED|PLANT=2
PING|v1|0
PONG|v1|0
```

## 6. HTTP API сервера

Рекомендуемые конечные точки:

- `POST /api/v1/device/{device_id}/heartbeat`
- `GET /api/v1/device/{device_id}/commands`
- `POST /api/v1/device/{device_id}/ack`
- `POST /api/v1/device/{device_id}/result`
- `POST /api/v1/device/{device_id}/state`
- `POST /api/v1/device/{device_id}/event`
- `POST /api/v1/device/{device_id}/time`

Упрощённая схема:

- `GET /commands` возвращает одну строку команды или пустой ответ;
- `POST /ack`, `POST /result`, `POST /state`, `POST /event` принимают одну строку протокола;
- `POST /time` либо `GET /time` используется для синхронизации времени, если нет RTC.

Пример ответа сервера на `/commands`:

```text
CMD|v1|104|LIGHT_TIMER_ENABLE|STATE=1
```

## 7. Внутреннее разбиение на модули

### 7.1 `TransportEsp8266`

Ответственность:

- настройка `ESP-01`;
- подключение к Wi-Fi;
- выполнение HTTP-запросов;
- чтение и запись строковых сообщений;
- отслеживание статуса связи;
- попытки переподключения.

Публичный интерфейс:

```cpp
bool begin();
bool ensureConnected();
bool httpGet(const char* path, char* out, uint16_t outSize);
bool httpPost(const char* path, const char* body);
ConnectionState getConnectionState();
```

### 7.2 `Protocol`

Ответственность:

- разбор строки в структуру команды;
- сборка `ACK`, `RES`, `ERR`, `STATE`, `EVT`;
- валидация обязательных полей;
- экранирование специальных символов при необходимости.

Публичный интерфейс:

```cpp
bool parseMessage(const char* raw, Message& out);
bool buildAck(uint16_t id, char* out, uint16_t outSize);
bool buildResult(uint16_t id, const char* status, char* out, uint16_t outSize);
bool buildError(uint16_t id, ErrorCode code, const char* arg, char* out, uint16_t outSize);
bool buildSnapshot(const RuntimeState& state, char* out, uint16_t outSize);
```

### 7.3 `CommandRouter`

Ответственность:

- определение типа команды;
- маршрутизация по подсистемам;
- защита от повторной обработки одинакового `command_id`;
- возврат унифицированного кода результата.

Публичный интерфейс:

```cpp
CommandResult handle(const Message& message, RuntimeState& state, ConfigStore& config);
```

### 7.4 `RuntimeState`

Ответственность:

- хранение текущего живого состояния в RAM;
- данные по свету, поливу, датчикам, соединению, ошибкам;
- метки активных ручных режимов;
- текущие флаги выполнения.

### 7.5 `ConfigStore`

Ответственность:

- сериализация настроек в `EEPROM`;
- загрузка конфигурации при старте;
- миграция схемы по версии;
- проверка целостности через `CRC`.

### 7.6 `EventLog`

Ответственность:

- кольцевой буфер последних событий в RAM;
- накопление событий до отправки на сервер;
- сброс после успешной публикации.

## 11. EEPROM layout

Рекомендуемая схема хранения:

```text
0x000 - 0x003  magic
0x004 - 0x005  schemaVersion
0x006 - 0x007  totalSize
0x008 - 0x009  crc16
0x00A - ...    PersistedConfig payload
```

Правила:

- при старте читается `magic`;
- если `magic` неверный, конфиг сбрасывается в дефолтный;
- если `schemaVersion` не совпадает, выполняется миграция или сброс;
- если `crc16` не совпадает, конфиг считается повреждённым;
- запись в `EEPROM` производится только при изменении конфигурации;
- не записывать конфиг на каждом цикле.

Что сохраняется:

- шаблоны света;
- активный шаблон;
- включён ли таймер света;
- режимы растений;
- пороги влажности;
- сетевые настройки;
- статические системные параметры.

Что не сохраняется постоянно:

- текущие логи;
- сырые измерения влажности;
- временное состояние HTTP-соединения;
- служебные буферы транспорта.

## 12. Слой интерфейсов к бизнес-логике

Чтобы другой разработчик мог реализовать доменную логику независимо, вводятся интерфейсы:

```cpp
bool applyLightManualCommand(uint8_t state, uint8_t priority, uint32_t durationSec, RuntimeState& stateRef);
bool setLightTimerEnabled(uint8_t enabled, RuntimeState& stateRef);
bool selectLightTemplate(uint8_t templateIndex, RuntimeState& stateRef);
bool setPlantMode(uint8_t plantIndex, uint8_t mode, RuntimeState& stateRef);
bool startManualWatering(uint8_t plantMask, RuntimeState& stateRef);
void tickSchedulers(uint32_t nowEpoch, RuntimeState& stateRef);
void updateSensors(RuntimeState& stateRef);
```

То есть модуль обмена не обязан знать, как именно вычисляется следующее событие таймера. Он только:

- принимает команду;
- проверяет параметры;
- вызывает нужную функцию;
- обновляет состояние;
- сохраняет конфиг при необходимости;
- отправляет результат.

## 14. Формат snapshot

Полный снимок должен собираться одной командой и возвращаться одной строкой или несколькими чанками.

Базовый компактный вариант:

```text
STATE|v1|0|SNAPSHOT|LIGHT=ON|LTIMER=1|LTPL=1|LMANUAL=HIGH|P1M=430|P1T=500|P1MODE=MOISTURE|P1W=0|P2M=610|P2T=550|P2MODE=TIMER|P2W=1|WIFI=1|SERVER=1|ERR=0
```

Если строка становится слишком длинной, использовать несколько сообщений:

```text
STATE|v1|0|LIGHT|LIGHT=ON|LTIMER=1|LTPL=1|LMANUAL=HIGH
STATE|v1|0|PLANT|INDEX=1|MOISTURE=430|THRESHOLD=500|MODE=MOISTURE|WATERING=0
STATE|v1|0|PLANT|INDEX=2|MOISTURE=610|THRESHOLD=550|MODE=TIMER|WATERING=1
STATE|v1|0|SYSTEM|WIFI=1|SERVER=1|ERR=0
```

Для `Uno/Nano` второй вариант безопаснее.

## 16. Основной цикл прошивки

Рекомендуемая логика `loop()`:

1. Обновить watchdog-таймеры и локальные таймеры.
2. Обновить датчики.
3. Выполнить `tickSchedulers(now)`.
4. При необходимости завершить ручные режимы.
5. Проверить Wi-Fi и состояние транспорта.
6. Если пришло время heartbeat, отправить heartbeat.
7. Если пришло время poll, запросить новую команду.
8. Если пришла команда, распарсить и обработать.
9. Если есть отложенные события, отправить их.
10. Если состояние изменилось, отправить `STATE`.

Важно:

- все операции должны быть неблокирующими настолько, насколько это возможно;
- длинные задержки `delay(...)` нужно минимизировать;
- любые повторы по сети делать через счётчики и таймауты.

## 17. Восстановление после перезагрузки

При старте:

1. Инициализировать GPIO.
2. Загрузить конфиг из `EEPROM`.
3. Проверить `CRC` и версию.
4. Если конфиг повреждён, восстановить дефолтный.
5. Восстановить постоянные режимы и шаблоны.
6. Поднять `ESP-01`.
7. Подключиться к Wi-Fi.
8. Синхронизировать время.
9. Отправить `STATE` с признаком старта.

После перезагрузки нужно гарантировать:

- шаблоны света восстановлены;
- выбранный шаблон восстановлен;
- режимы растений восстановлены;
- пороги влажности восстановлены;
- таймерные флаги восстановлены;
- устройство может снова принять команды без ручной настройки.

## 18. Отправка событий и логирование

Логирование делится на 2 уровня:

- внутренний буфер последних событий;
- публикация важных событий на сервер.

Типы логируемых событий:

- входящая команда;
- изменение состояния света;
- включение и выключение полива;
- смена режима растения;
- ошибка транспорта;
- ошибка парсинга;
- ошибка исполнения;
- перезагрузка;
- восстановление конфига.

Формат события:

```text
EVT|v1|0|LIGHT_CHANGED|STATE=ON
EVT|v1|0|WIFI_RECONNECTED
EVT|v1|0|CONFIG_RESTORED|SOURCE=EEPROM
```

## 19. Расширяемость

Чтобы позже добавить несколько ламп, помп и датчиков, уже сейчас нужно:

- использовать сущности с индексами или `id`;
- не шить в код одну-единственную лампу как особый случай;
- закладывать `device_type` и `target_id` в будущие команды;
- держать доменные структуры массивами, а не одиночными переменными.

Пример направления для `v2`:

```text
CMD|v2|401|LIGHT_MANUAL|TARGET=2|STATE=ON|PRIORITY=HIGH
CMD|v2|402|WATERING_MANUAL_START|TARGET=3
```

## 20. MVP по этапам

### Этап 1

- поднять UART и `ESP-01`;
- отправлять `PING/PONG` или heartbeat;
- сделать `GET_SNAPSHOT`.

### Этап 2

- реализовать хранение конфига в `EEPROM`;
- реализовать команды света;
- реализовать `ACK/RES/ERR`.

### Этап 3

- реализовать команды полива;
- реализовать события;
- реализовать защиту от дублей команд.

### Этап 4

- добавить time sync;
- добавить расширенное состояние;
- отладить восстановление после перезагрузки.

## 21. Нерешённые вопросы

Перед кодированием желательно зафиксировать:

- есть ли отдельный `RTC` модуль;
- сколько растений должно поддерживаться реально;
- сколько шаблонов света нужно в первой версии;
- сервер уже существует или мы задаём API с нуля;
- нужен ли `HTTPS` или достаточно `HTTP`;
- кто именно реализует слой бизнес-логики и в каком интерфейсе ему удобнее работать.
